# MuPa · landing / futura Home del sitio

Sitio público del **Museo Paleontológico de San Juan (MuPa)**, Argentina. Cliente institucional (Gobierno de San Juan + UNSJ + Fiduciaria San Juan). Trabajo freelance a precio fijo (USD 3.500, 8-10 semanas). Esta carpeta es la landing "one page" pedida por el museo, construida para convertirse en la Home del sitio definitivo (React + Vite + Express + PostgreSQL + Mercado Pago Checkout Pro; el spike de Mercado Pago ya funciona en la PC personal del desarrollador y no está en este repo).

## Stack y comandos
- **Dos ramas desde el 09/10/2026** (E0 de `docs/plan-panel-admin.md`): `master` es el sitio completo que va a Render (Express 5 con render en el servidor en cada pedido, y desde E1 Postgres y el panel en `/administracion`); **la landing estática publicada en Hostinger vive en la rama `landing`** (apunta a `5049395`, lo publicado): los arreglos de la landing hasta el corte del dominio se hacen ahí y se suben como siempre (ver "Para actualizar el sitio"). Lo que sigue es `master` salvo que diga otra cosa.
- React 19 + Vite 8 + Tailwind 4 (`@tailwindcss/vite`) + **Lenis** (scroll suave) en el navegador; Express 5, helmet, zod y Sequelize 6 + pg en el servidor, y desde E1 umzug (migraciones), argon2 (contraseñas) y express-rate-limit (límites de intentos). `vite.config.js` usa `base: '/'` (en `landing`, `'./'`, para servir desde una subcarpeta de Hostinger).
- `npm run dev`: Express con Vite adentro (SSR y recarga en caliente) en http://localhost:5300/, el puerto de `measure.mjs` (no el 5173 de Vite: otro proyecto con Vite en esta PC lo toma en [::1] y "localhost" abría ese; `npm run dev` ahora se niega a arrancar si el puerto está ocupado en [::1]; otro puerto: `npm run dev -- --port N`); lee `.env` (copiarlo de `.env.example`); sin base, `SIN_BASE=1` (o `maximo` / `vacio`: el museo de ejemplo). `npm run dev:vite`: Vite suelto en 5302, para retocar efectos. `npm test`: `node:test` sobre `server/pruebas/`, en serie; las pruebas con base necesitan `mupa_test` (`DATABASE_URL_TEST` en `.env`) y sin ella se saltean (ver Verificación).
- `npm run build` borra `dist/` entero y deja `dist/client/` (la plantilla `index.html` con las marcas `<!--head-->`, `<!--app-->` y `<!--estado-->`, `assets/` con hash y lo de `public/`) y `dist/server/entry-server.js`. `npm start` sirve ese build; **la producción en local** es `NODE_ENV=production PORT=5183 URL_PUBLICA=http://127.0.0.1:5183/ npm start` (en ese host, GA4 activo y sin `noindex`, como mupa.ar; sin `NODE_ENV=production`, con `noindex` y sin GA4). Node ≥ 22.9 (`--env-file-if-exists`; esta PC tiene la 22.19); Render usa la 24 (`.node-version`).
- **El `dist/` de `master` no se sube nunca a Hostinger**: `dist/client/index.html` es una plantilla vacía y mupa.ar quedaría en blanco. `npm run build:preview`, `npm run preview` y el prerenderizado (`tools/prerender.mjs`, que dejaba la página dentro del `#root` del `index.html`) son de la rama `landing`; en `master` el HTML lo arma Express en cada pedido (`server/ssr.js`).
- Windows: si `npm` no aparece en el PATH del proceso, usar `C:/Program Files/nodejs/npm.cmd`.
- **Base y migraciones (E1, 13/10/2026)**: PostgreSQL 17 local, `mupa_dev` para `npm run dev` y `mupa_test` para `npm test` (rol `mupa`; en `.env`, `DATABASE_URL`, `DATABASE_URL_TEST` y `DB_SSL=0`; cada archivo de pruebas con base borra `mupa_test` entera, ver Verificación). `npm run migrar` aplica las migraciones pendientes (`server/db/migraciones/`, umzug: el esquema lo cambian solo ellas, nunca un `sync`; en Render es el pre-deploy); `npm run migrar:atras` deshace la última y en producción, o contra una base que no es local, exige `npm run migrar:atras -- --confirmo-borrar-datos`; `node --env-file-if-exists=.env server/db/migrar.js estado` lista aplicadas y pendientes; `npm run semilla:ejemplo` carga el museo, el horario y tarifas de ejemplo (marcados "EJEMPLO ·", sin usuarios; se puede repetir; solo contra una base local, nunca en producción); `npm run crear-admin -- --email <correo> --nombre "<nombre>"` (cuenta nueva) y `npm run restablecer-admin -- --email <correo>` (cuenta existente: queda admin, activa y sin sesiones) son la llave de emergencia: dan una temporal de 72 h que se imprime una sola vez, en la terminal, y que hay que cambiar en el primer ingreso. En `mupa_dev` quedaron, al 13/10/2026, la semilla y dos cuentas de prueba sin contraseña conocida (`prueba-e1-admin@example.com`, admin, y `prueba-e1-editora@example.com`, editora): para entrar con la primera, `npm run restablecer-admin -- --email prueba-e1-admin@example.com`.
- **Admin local para probar el panel**: con `mupa_dev` migrada (`npm run migrar`), `npm run crear-admin -- --email <tu-correo> --nombre "<tu nombre>"` y entrar con la temporal que imprime (hasta E2.1 no hay pantallas: la API se prueba con curl, con el `Origin` del propio sitio y `Content-Type: application/json` en todo lo que no es GET).

## Convenciones
- Comentarios, nombres y textos en español.
- Tailwind 4: clases estáticas siempre (nada de `bg-${x}`); tokens en `@theme`; CSS base propio SOLO dentro de `@layer base` (fuera de capa le gana a las utilidades); valores arbitrarios de tamaño con prefijo: `text-[length:clamp(...)]`. Desde E0 (09/10/2026) Tailwind escanea solo `src/` (`@import "tailwindcss" source(".")` en `index.css`): una clase que aparece solo en un `.md` o en `tools/` ya no se genera. El CSS de la landing traía siete así, sacadas de este archivo y de `docs/`, que ningún componente usa (`px-10`, `drop-shadow`, `ease-in-out`, `aspect-[1440/1195.5]` sin `md:`, `lg:mt-12`, `lg:mt-[calc(0.73125rem-0.4212em)]` y un `text-[length:clamp(...)]`).
- Accesibilidad: un solo h1; secciones con `aria-labelledby`; acordeón con `aria-expanded`/`aria-controls`; `prefers-reduced-motion` respetado; imágenes con `alt` real.
- No commitear ni pushear sin que el desarrollador lo pida.

## Decisiones ya tomadas (no re-discutir salvo que el desarrollador lo pida)
- **Tipografía** (V03 de la diseñadora, confirmado por el desarrollador el 25/09/2026; antes Geologica, del Figma V02 del 21/09, que a su vez había reemplazado a Google Sans Flex del `.ai`): **Google Sans Flex** para todo el texto y **Roboto Mono** (variable 400..700) en las etiquetas EJE NARRATIVO / VISIÓN / MISIÓN, los años de la línea de tiempo y el lema de Ciencia. El PDF del V03 embebe 10 subconjuntos de GoogleSansFlex (nombre real leído de la tabla `name` con pdf.js) y ninguno de Geologica; la familia se publicó en Google Fonts en noviembre de 2025 con licencia **SIL OFL 1.1 sin Reserved Font Names**, así que se puede usar. **Las dos fuentes van en el repo** (`src/assets/fonts`, declaradas en `index.css`; ya no hay ningún pedido a fonts.googleapis.com, que demoraba ~530 ms el primer texto): Google Sans Flex recortada a latin+latin-ext con `tools/subset-fuente.mjs` (93 kB, ejes wght 100..1000 y **wdth 100..130**, tamaño óptico fijo en 20, que es la óptica del V03 —si quedara variable, el navegador lo movería con cada cuerpo y los anchos dejarían de coincidir—) y el woff2 variable de latin de Roboto Mono que sirve Google, guardado tal cual (33 kB). La original (4 MB) no se versiona: el script dice de dónde bajarla. El desarrollador eligió el cambio el 25/09/2026 porque "la tipografía se siente distinta a la del PDF": medido, Geologica pinta ~40 % más tinta a igual cuerpo y su Bold es ~19 % más angosta, así que el mismo texto se leía más pesado. **Pesos del V03** (deducidos midiendo los avances de cada subconjunto contra la fuente real, calce exacto al entero): **100** en los títulos de sección; **300** en los párrafos y en los textos de los hitos; **400** en las líneas fijas del titular y en los textos de los ejes; **600** en el hito activo; **700** en los destacados; **755 con el eje de ancho en 130** en "sanjuaninos" (`[font-stretch:130%]`: en el V03 la palabra está expandida, no solo en negrita, y con la fuente autoalojada el eje existe; medido, 7,578 em contra los 7,571 del PDF). Roboto Mono: Medium 500 en las etiquetas, Regular 400 en los años y Bold 700 en el año activo. Fallbacks locales con `size-adjust` recalculado el 25/09/2026 contra el peso 300 (Segoe UI 100,82 %, Roboto 99,93 %, Arial 99,78 %) y ascent/descent de Google Sans Flex (0,966/0,286 em, comprobados contra el alto de línea normal, 1,252 em). **Tamaños del V03 a 1440** (PDF a 1920 × 0,75): párrafos 22,5/36 (interlineado 1,6), textos de los ejes 16,5/27, hitos 21/33 con el año en mono a 0,8 em, titular 64/76,8, etiquetas mono 24, **títulos de sección** (V04, 28/09/2026: Identidad en dos líneas a 78,75 px = 5,47vw con interlineado 1,01, Obra 61,5 = 4,27vw con 1,16, Áreas 48,75 = 3,386vw con 1,38, todos Thin salvo Áreas en Light con la segunda línea Bold, y los nombres de las bandas también a 48,75; hasta entonces Identidad iba a `clamp(2rem, 7vw, 6.5rem)` = 100,8 px en una línea y Obra a 5,25vw, y antes, hasta el 25/09/2026, a `clamp(2rem, min(7vw, (100svh − 38.5625rem)/2.1), 6.5rem)`: 100,8 px a 1440x900 y 104 de 1486 de ancho para arriba. El V03 los tenía a 128, pero el 25/09/2026 el desarrollador pidió bajarlos "para que abarque más pantallas": el grupo enganchado de Obra (título + 16 + lista 585) tiene que entrar en la ventana, así que además del ancho el tamaño mira el **alto** y se achica solo cuando ese es el límite —a 1366x768 da 72 px y el grupo entra igual—. Medido: se engancha en 1280x720, 1280x800, 1360x768, 1366x768, 1152x864, 1536x864, 1440x900, 1470x956, 1512x982, 1600x900, 1680x1050, 1920x969 y 1920x1080; queda suelto en 1024x768, donde la columna de los hitos se angosta y la lista pasa a 717 px). Columnas del V03: párrafo de la intro y cierre de Identidad 593/590 px, texto de los ejes y párrafo de Obra 419.
- **Titular con parallax**: las dos líneas fijas ("un museo de" / "hecho por"; el V03 sacó "y para" el 25/09/2026) van alineadas a la derecha en la columna izquierda y "sanjuaninos", en negrita, en la derecha; con el scroll la palabra baja de fila en fila formando "un museo de sanjuaninos" y "hecho por sanjuaninos". El scroll no arrastra la palabra: solo elige la fila (umbral a mitad de cada tramo, con histéresis de 0,1 tramo para que no titile) y la palabra viaja sola con una animación de 360 ms (Web Animations sobre transform; x1,41 si son dos filas), cuya duración no depende de la velocidad del scroll, así las transiciones se ven idénticas con rueda, trackpad o touch (medido: 4,7-5,5 px por frame en viajes de una fila, 6-7,5 en viajes de dos filas con rueda rápida; elegido el 17/09/2026 frente a un parallax ligado al scroll, a CSS scroll-driven y a GSAP/Motion/Lenis). Si cambia el destino a mitad de viaje sigue desde donde está, empalmando la velocidad si va para el mismo lado; si se invierte, frena y vuelve (límite conocido de Web Animations: con el hilo principal trabado justo en ese momento puede verse un salto de hasta ~25 px; `reverse()` tampoco lo evita, medido). Sin animación: primer pintado, reentrada en vista, cambios del recorrido (alto de las filas: fuentes, ancho), saltos desde lejos (más de medio viewport entre dos eventos de scroll con el titular fuera de vista antes o después: Inicio/Fin, Ctrl+F, AvPág y anclas sin scroll suave; los del hilo principal se pintan en el mismo frame, los del compositor sin scroll suave, como la rueda de muescas grandes o el clic en el riel, muestran 1 frame la fila vieja; si el titular estaba a la vista antes y después, el viaje sigue) y todo scroll anterior al primer gesto de la persona (rueda, tecla, toque o clic) o a 1 s después de `load` o del montaje si `load` ya pasó (la restauración al cargar o al volver atrás; un dedo apoyado con la página en blanco no abre la compuerta, la abre el temporizador). El efecto empieza cuando el bloque entra por el 80 % del alto y ocupa max(0,3 vh, 240 px) de scroll **por tramo** (eran max(0,6 vh, 480 px) para los dos tramos de tres filas; desde el V03 el recorrido es por tramo, así cada fila cuesta el mismo scroll que antes y con dos filas el efecto termina en la mitad de scroll), salvo que el final quede clavado en 0,15 vh (en móvil ~220 px: con un flick la frase del medio no se lee quieta, con el dedo lento sí; decidido dejarlo así el 18/09/2026); debajo de lg ese recorrido se estira un 10 % corriendo el final (a 375x812, ~245 px). El 22/09/2026 el desarrollador pidió +25 % en todos los efectos por pasos con el dedo ("las animaciones se pasan demasiado rápido con el touch") y ese mismo día, porque un usuario de prueba sintió el scroll del teléfono trabado, un punto medio: +10 % sobre lo del 21/09 (titular, carrusel, collage e hitos); alto del viewport cacheado en pantallas sin hover (la barra del navegador móvil no corre los umbrales); en reposo transform redondeado a píxel entero. ## Compatibilidad entre navegadores (leer antes de tocar scroll, sticky o alturas)
Lo que se sabe al 30/09/2026, de las pruebas del desarrollador en su celular Android, en un iPhone (desde un link de Instagram) y en una Mac con Safari, y del análisis del código con cuatro lentes y verificación adversarial. Acá no hay iPhone ni Safari: solo Chrome headless en Windows, así que lo de Safari se razona, se simula en Chrome hasta donde se puede y **lo confirma el desarrollador en el iPhone**. Cuando reporte algo del iPhone, mirar primero estas tres cosas: el alto de la pantalla que dejan las barras, el anclaje de scroll y la inercia.
- **Alto de pantalla.** Safari en iPhone deja **~664 px a 390 de ancho y ~635 a 375** con la barra de direcciones y la de abajo a la vista (el navegador de Instagram, parecido o menos); Chrome en Android deja ~780 a 412. Todo lo que se engancha en celular (trío de Obra, bloque de etiquetas de Áreas, lista de hitos) tiene que entrar en esos altos o tener un modo alternativo medido por JS (`data-obra="trio-compacto"`, `data-libre`, `data-hitos-libres`), nunca un corte fijo por CSS. Medir siempre también a **390x664 y 375x635** (los iPhone), no solo a 375x812.
- **La barra de Safari se contrae y se expande en pleno gesto**: `window.innerHeight` cambia unos 80-120 px y dispara `resize` sin que cambie el ancho. Regla: **los altos se cachean sin hover y solo se renuevan si cambia el ancho** (giro) o si el cambio pasa de 200 px (todos los hooks lo hacen: `useScrollPorPasos`, `useHitoActivo`, `useAcordeonScroll`, `altoViewport` de Areas.jsx), las decisiones de modo se toman con ese alto cacheado, y el CSS usa **solo `svh`** para alturas de bloques (nunca `vh`, que en iOS es el viewport grande, ni `dvh`, que cambia con la barra y mueve el layout). Un listener de `resize` nuevo tiene que seguir la misma regla o no recalcular nada con el mismo ancho: desde el 30/09/2026 los tres hooks que escuchan `resize` (`useScrollPorPasos`, `useHitoActivo`, `useAcordeonScroll`) lo ignoran directamente cuando solo cambió el alto en menos de 200 px sin hover (`alRedimensionar`), así la barra no fuerza ningún layout; la guarda va en el listener y no dentro de `remedir`, que también lo llaman el ResizeObserver, `fonts.ready` y el cambio de reduced-motion. Con eso, la barra quedó refutada como causa de los tirones del acordeón (30/09/2026). Del mismo análisis, para que el cuadro en que se abre un panel pese menos en un iPhone: la foto del panel lleva `decoding="async"` y se decodifica apenas carga (`decode()` en `onLoad`; `requestIdleCallback` no existe en Safari), y `Banda` va en `memo` para que abrir una no vuelva a renderizar las otras tres.
- **Safari no tiene anclaje de scroll** (`overflow-anchor`; Chrome y Firefox sí; iOS 27.0-27.2 tampoco, según caniuse, aunque WebKit ya lo tiene en su versión de prueba): si algo por encima de la pantalla cambia de alto, en Chrome el navegador corre el scroll solo y no se nota; en Safari lo que se ve salta salvo que el código corrija el scroll (`mantenerEnPantalla`). Y **el scroll de iOS es asíncrono, con la inercia en el proceso de UI**: un `scrollTo` en plena inercia o con el dedo en movimiento pelea con el gesto (corta la inercia o llega a una posición atrasada) y se siente como un tirón. Por eso el acordeón tiene un **camino de Safari** (`CAMINO_SAFARI = !CON_ANCLAJE || ES_IOS`; `ES_IOS` es `CSS.supports('-webkit-touch-callout', 'none')`, que solo existe en iOS/iPadOS: así el día que Safari tenga anclaje el iPhone no pierde las protecciones). Reglas: (1) **no cambiar el alto de nada que esté por encima de la pantalla mientras el scroll se mueve con el dedo**: en el camino de Safari esos cambios esperan al scroll quieto (`QUIETO_DEDO`, 450 ms sin eventos: la cola de la deceleración y el rebote de iOS mueven la página sin disparar `scroll`; 200 con puntero fino) y al dedo levantado (`touchstart`/`touchmove` lo apoyan, `touchend`/`touchcancel` lo levantan; con un `touchend` perdido se cierra igual a los ~2 s), **con una excepción: el `touchstart`** (`alTocar`): tocar el vidrio frena la inercia antes de que el gesto nuevo mueva la página, así que ahí se cierran las bandas de arriba ya enteras fuera de la pantalla; sin eso, leyendo con flicks seguidos nunca había 450 ms de quietud y las de arriba no se replegaban (lo vio el desarrollador el 30/09/2026), también en el final de la página (ahí, si el toque llega durante el rebote, el delta de la corrección queda fuera del rango y el rebote se corta de golpe unos pocos px; se aceptó el 30/09/2026 porque sin cerrar en el final, con un flick hasta abajo y un toque para volver a subir, las bandas de arriba no se cerraban nunca); en Chrome se cierran en cuanto salen de la pantalla, igual que antes; (2) al final del documento iOS rebota (`scrollY` pasa del máximo y vuelve): las medidas que dependen de la posición se hacen como si el scroll estuviera en el máximo (`rebote` en `useAcordeonScroll`), pero el cierre con el scroll quieto no espera por el rebote (mientras rebota dispara `scroll`; un `scrollY` que sigue pasado del máximo es un margen fijo de iOS, y esa espera hacía que en el iPhone no se cerraran); (3) cualquier cambio de layout + corrección del scroll va en el mismo task, después de una lectura de layout, y la corrección es `scrollBy` (delta), no `scrollTo` (absoluto): en WebKit el delta se suma a la posición real del UIScrollView, y el `scrollY` del proceso web va uno o dos cuadros atrás durante un gesto; (4) después de una corrección iOS puede mandar un evento `scroll` con la posición vieja (cuadro fantasma): el acordeón saltea la medida que difiere del `scrollY` corregido en más del 80 % de lo plegado dentro de los 100 ms siguientes (`sospechosa`); (5) la regla de "final de página" se evalúa contra el largo final del documento (lo que a los paneles les falta crecer, `pendiente`, más lo que va a crecer la banda que esa misma medida abre, `extra`), y al terminar una transición de alto se vuelve a medir (`transitionend`). **La apertura por scroll en el camino de Safari es una aparición y no un crecimiento** (ver Áreas): creciendo durante 1 s, el final del documento avanzaba de a poco justo cuando el flick llegaba a él (en iOS, un rebote en cada cambio de banda) y el crecimiento necesita al hilo principal en cada cuadro. Lo que estaba a la vista debajo baja deslizándose y desvaneciéndose (200-350 ms, en el compositor) con el mismo movimiento que tenía el crecimiento; con flicks rápidos, directa. **Regla general que salió de todo esto: nada puede quedar corrido de su lugar de layout mientras la persona puede scrollear hasta verlo** (o se ve un hueco donde tiene que estar, o se lo ve saltar al volver): los desplazamientos con transform tienen que ser cortos y terminar invisibles. **Lo que se probó y se descartó** (30/09/2026): (a) reservar el alto final del panel durante la apertura (evitaba el rebote pero dejaba hasta 1280 px negros entre la última banda y el pie); (b) abrir moviendo con `transform` lo de abajo (FLIP: el panel con su alto final de una vez, las bandas siguientes y el pie corridos hacia arriba y bajando, y una cortina del color del fondo destapando el panel): era fluida e idéntica a la vista (capturas congeladas a los 500 y 800 ms con los mismos píxeles), pero la revisión adversarial mostró que un flick que llegaba al final durante la apertura dejaba fondo vacío debajo del pie (hasta una pantalla entera), que dos aperturas solapadas sacaban las animaciones del compositor (`composite: 'add'` no se acelera ni en Chrome ni en WebKit) y que los cierres y reaperturas a medias saltaban; (c) bloquear el cierre inmediato en Android por `sinHover` (ahí el cierre con anclaje está medido y aprobado). Si Safari llega a tener anclaje y en el iPhone vuelven los tirones, el camino de Safari ya se mantiene por `ES_IOS`; lo que habría que mirar es si el anclaje de WebKit, al compensar el plegado en pleno scroll, corta la inercia.
- **Sin puntero fino** (celulares y tablets, `any-pointer: fine` falso) **no se crea Lenis** y el scroll con el dedo es el nativo del navegador; `(hover: none)` es verdadero. En Safari de Mac con trackpad sí hay Lenis y tampoco hay anclaje: el acordeón sigue el camino sin anclaje (pliega a la vista con el scroll quieto, como en Chrome de escritorio).
- **Qué no existe en Safari viejo**, por si el iPhone tiene menos de iOS 16: `overflow: clip` (16.0; sin él, el patrón de piedritas de Áreas desborda a lo ancho y Safari deja panear de costado), `@container`/`cqw` del collage (16.0), transición de `grid-template-rows` de los paneles (16.0), `svh` y `:has` (15.4), `scrollTo({ behavior: 'instant' })` (15.4), `scrollbar-width` (18.2; lo cubre `::-webkit-scrollbar`), `requestIdleCallback` (con respaldo en `analitica.js`). Tailwind 4 pide Safari 16.4 o más. Si algo no anda en el iPhone, pedir modelo y versión de iOS antes de buscar en el código.
